Section 12: Cloud Logging.

Cloud Logging is the central service on Google Cloud Platform for collecting, routing, storing, and analyzing log data. Understanding how logs flow through the system is essential for both troubleshooting and for designing a good observability strategy.

Let's start with how logs flow. Logs originate from a variety of sources, including Google Cloud services themselves, GKE which stands for Google Kubernetes Engine clusters, Compute Engine virtual machines using the Ops Agent, and your own custom applications. Once generated, all of these logs flow into the Log Router. The Log Router is the decision-making layer. You configure it with inclusion filters and exclusion filters to control which logs are kept and which are dropped. After the Log Router processes a log entry, it sends the log to one or more destinations called Log Sinks. There are four possible sink destinations. The first is Cloud Logging Buckets, which is the default storage location. The second is BigQuery, which is used when you need to run analytical queries on your logs. The third is Pub/Sub, which is used for streaming logs to third-party systems or external services. The fourth is Cloud Storage, which is used for long-term archival at low cost.

Now let's look at the different types of logs. Platform logs are written by Google Cloud services themselves. A good example is VPC Flow Logs, which capture information about network traffic entering and leaving your virtual private cloud. Security logs include Audit logs and Access Transparency logs. Audit logs record who did what and when across your Google Cloud resources, while Access Transparency logs record actions taken by Google staff when they access your data. User-written logs come from your own applications, written either through the Logging API, the Ops Agent, or simply by printing to standard output in a containerized environment. Finally, there are logs from multi-cloud and hybrid cloud environments, meaning logs that originate from outside of Google Cloud entirely.

Moving on to the key features of Cloud Logging. Log-based metrics allow you to create counter or distribution metrics derived directly from log data using filters. This means you can turn specific log patterns into metrics that trigger alerts in Cloud Monitoring. The Log Explorer is the primary troubleshooting interface. It lets you stream live logs, view a histogram of log volume over time, and apply filters to narrow down exactly what you're looking for. Log Analytics is a more powerful querying experience powered by BigQuery. It allows you to run standard SQL queries directly against your log data for deep analysis.

It's important to note that Log Analytics requires you to upgrade a logging bucket to enable the feature, and this upgrade is permanent. Once you enable Log Analytics on a bucket, you cannot downgrade it, so make that decision carefully.

Finally, let's cover log retention defaults. There are two built-in log buckets that every Google Cloud project has. The first is called the Required bucket. It stores Admin Activity logs and System Event logs and retains them for 400 days. This bucket is free, and you cannot delete it or reduce its retention period. The second is called the Default bucket. It retains logs for 30 days and is included in the standard Cloud Logging pricing. Beyond these two, you can create custom buckets with configurable retention periods, and these are billed on a per-gigabyte basis. Understanding these retention defaults is important when planning for compliance requirements or long-term log archival.
