Section 16: Terraform on GCP.

Terraform is an infrastructure-as-code tool that lets you define and manage cloud resources using configuration files. Let's start by walking through the standard Terraform workflow, which has seven steps.

Step one is Scope, where you identify what resources your infrastructure needs. Step two is Author, where you write the configuration files using Terraform's language. Step three is Initialize, which is where you run the terraform init command. This downloads the provider plugins needed to communicate with GCP. Step four is Plan, where you run terraform plan to preview what changes Terraform would make. Importantly, this step makes no actual changes to your infrastructure. Step five is an optional Validate step, where you can run a gcloud command to check your plan against organizational policy constraints before applying anything. Step six is Apply, where you run terraform apply to actually create or update your infrastructure. Step seven is Destroy, where you run terraform destroy to tear down all the resources that Terraform manages.

Now let's talk about HCL, which stands for HashiCorp Configuration Language. This is the syntax used to write Terraform configuration files. The basic structure involves declaring a resource block with a resource type and a name, followed by the configuration arguments for that resource. For example, you might declare a Google Compute Network resource and give it a name and settings. Once a resource is declared, you can reference its attributes in other parts of your configuration using a dot-notation path that includes the resource type, the resource name, and the attribute you want.

Moving on to the key building blocks of a Terraform configuration. A resource block declares an infrastructure object you want to create or manage. A variable block lets you parameterize your configuration so the same files can be used in different environments. An output block exports a resource attribute after the apply step completes, making it available to other configurations or for display. A module block lets you group reusable resources together and call them as a unit. A data block lets you read information about an existing resource that is not managed by your current configuration. And a depends-on argument lets you declare an explicit dependency between resources.

It is important to understand the difference between implicit and explicit dependencies. Terraform automatically detects implicit dependencies when one resource references an attribute of another resource. If resource A uses the ID of resource B, Terraform knows to create B first. Explicit dependencies are declared manually using depends-on, and you need them when the dependency exists logically but is not visible through attribute references in the configuration.

Now let's talk about modules. In Terraform, a module is simply any directory that contains configuration files. The root module is the directory where you run your plan and apply commands. Child modules are reusable components that the root module calls. Modules implement the DRY principle, which stands for Don't Repeat Yourself, by letting you define a pattern once and reuse it across environments or projects. It is good practice to pin module versions using a version argument so that changes to a shared module don't unexpectedly affect your deployments. Google publishes a set of pre-built GCP modules called the Cloud Foundation Toolkit, available on the Terraform Registry, which provide opinionated, best-practice patterns for common GCP infrastructure.

Let's cover Terraform state. Terraform uses a state file to keep track of what infrastructure it manages and what the current configuration looks like. You have two options for where to store state. Local state keeps the file on the machine where you run Terraform. This is fine for individual developers but is problematic for teams because the file isn't shared and sensitive data is stored in plaintext. Remote state stores the file in a Cloud Storage bucket. This is the right choice for teams because it provides native locking to prevent two people from applying changes at the same time, encryption at rest, IAM-controlled access, and automatic sharing.

There are several important best practices around state. Always use remote state for team environments and store it in a Cloud Storage bucket. Never store secrets in state files because they are stored in plaintext. Never manually edit the state file; use terraform state commands instead. Add your state files to your git ignore file so they are never accidentally committed to a code repository. And restrict access to the state bucket to build systems and privileged administrators only.

Finally, let's distinguish two validation commands. The terraform validate command checks your configuration for syntax errors only. It does not enforce any policies. The gcloud beta terraform vet command goes further and checks your plan against your organization's policy constraints before you apply it. This is the command to use when you want to catch policy violations early in the workflow.
